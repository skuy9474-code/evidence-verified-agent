# 코드 읽는 순서

처음부터 모든 파일을 읽을 필요는 없습니다. 이번 개선의 중심인 아래 파일부터 차례로 봅니다.

## 1. agent/validation.py — 답안 검사 담당자

수집한 자료를 정답지처럼 사용해 AI 답변을 비교합니다. 예를 들어 auth-service의 CPU 원본이 78이면, 답변에도 같은 시스템에 78이 연결되어 있어야 합니다. 어떤 부분이 틀렸는지 오류 목록을 반환합니다. 외부 AI 호출 없이 Python 코드로 검사합니다.

## 2. agent/answer_schema.py — 답변 양식과 화면 표시

AI에게 시스템·상태·수치·원인 가설·조치·한계를 정해진 JSON 항목으로 작성하게 합니다. JSON은 항목 이름과 값을 짝지어 저장하는 형식입니다. 이 파일은 그 항목들을 사람이 읽는 문장으로 표시합니다. AI가 수치를 잘못 썼다고 원본 값으로 몰래 고치지 않습니다.

## 3. agent/graph.py — 작업 순서 관리자

질문 분류 → 계획 → 조사 → 작성 → 검증 순서를 연결합니다. 검증에 실패하면 오류 사유를 넘겨 다시 작성하게 합니다. 작성은 총 세 번까지만 하며, 계속 실패하면 검증 보류 문구와 수집 근거만 제공합니다. 일반 대화는 별도 경로입니다.

## 4. agent/ollama_llm.py — 컴퓨터 안의 실제 AI 호출

로컬 Ollama에 질문을 보내고 JSON 답변을 받습니다. 이번에는 설치되어 있던 qwen3.5:2b를 사용했습니다. 모델 대기 중에도 서버가 진행 상태를 전달할 수 있도록 동기 호출은 작업 스레드에서 실행합니다.

## 5. agent/targets.py — 질문에 나온 시스템 이름 보존

질문이 billing-service를 가리키는데 AI가 auth-service를 조사하라고 하더라도, 질문에 명시한 billing-service를 조회하도록 맞춥니다. 미등록 시스템이면 원본 도구가 unknown을 반환하고 수치는 미확인으로 표시합니다.

## 6. server.py·web_chat.html — 요청 접수와 화면

서버가 조사와 검증 결과를 전달하고, 화면은 검증 사유와 최종 답변을 보여줍니다. 모델·자료 연결 실패는 성공 답변과 구분해 안내하고, 빈 질문과 전송 중 중복 요청을 막습니다. 진단 초안은 검증 전에 말풍선으로 내보내지 않습니다.

## 7. tests/·eval/ — 제대로 바뀌었는지 확인

단위 테스트는 수치 혼동·미확인 처리·재작성·최대 시도 후 보류 등을 검사합니다. 합성 사례 평가는 같은 답변에 기존 검사와 새 검사를 적용합니다. 실제 모델 평가는 로컬 AI와 MCP가 함께 동작하는지를 확인합니다. 두 결과를 섞어 실제 운영 정확도라고 말하지 않습니다.

## 발표에서 설명할 핵심

“기존에는 답변이 길고 번호가 있으면 통과했습니다. 저는 수집한 시스템별 상태와 수치를 기준으로 AI 답변을 비교하도록 바꿨습니다. 틀린 부분은 피드백으로 다시 작성하고, 계속 실패하면 통과시키지 않습니다. 다만 원인과 조치의 의미 전체를 검증하는 기능은 아닙니다.”
