## 3. 문제 정의 및 선정 이유

기존 프로그램은 시스템 상태와 대응 매뉴얼을 조회해 장애 진단 답변을 작성한다. 그러나 현재 답변 검증은 주로 ‘30자 이상인지’, ‘1)이라는 번호가 포함되어 있는지’를 확인한다. 따라서 형식이 맞더라도 수치를 잘못 인용한 답변이 통과할 수 있다. 또한 재작성 시도 횟수에 도달하면 검증에 실패한 답변도 통과시키는 처리가 있다.

이를 개선해 AI가 작성한 답변을 같은 요청에서 수집한 모니터링 근거와 대조하고, 불일치한 내용을 수정하도록 한다. 수업에서 배운 LangGraph의 검증·재작성 흐름과 MCP 데이터 조회를 활용하며, 동일 사례의 개선 전후 결과를 비교할 수 있어 이 주제를 선택했다.

## 4. 개선 목표 및 세부 기능

| 순번 | 영역 | 개선 내용 | 세부 계획 |
|---|---|---|---|
| 1 | 근거 대조 | 시스템별 상태·CPU·메모리 일치 검사 | 수집한 시스템 이름과 지표를 기준으로 답변의 상태·수치를 비교한다. |
| 2 | 누락·미확인 처리 | 근거가 부족한 답변 구분 | 조회한 시스템의 누락, 조회하지 않은 시스템의 추가, 미확인 값을 측정값으로 제시하는 문제를 검사한다. |
| 3 | 답변 구성 | 필수 항목 검사 | 모니터링 근거·원인 가설·권장 조치·한계 항목이 포함되어 있는지 확인한다. |
| 4 | 재작성 흐름 | 구체적 피드백과 최대 시도 후 보류 | 불일치 사유를 전달해 다시 작성하고, 총 3회 작성 후에도 통과하지 못하면 검증 보류로 처리한다. |
| 5 | 화면 표시 | 검증 과정과 결과 안내 | 검증 사유와 최종 결과를 표시하고, 검증 전 진단 초안이 먼저 노출되지 않도록 한다. |

예시: 모니터링에서 특정 시스템의 CPU가 78%로 조회되었는데 답변이 18%라고 작성되면, 불일치를 찾아 올바른 근거를 바탕으로 재작성하도록 한다. 이 숫자는 기능 설명을 위한 예시다.

## 5. 활용 기술

- **FastAPI:** 사용자 요청과 검증 결과 전달
- **LangGraph:** 작성 → 검증 → 피드백 → 재작성 흐름 구성
- **MCP:** 기존 모니터링 데이터와 대응 매뉴얼 조회
- **규칙 기반 검증:** 시스템별 상태·수치 대조와 필수 항목 검사
- **SSE·Vue:** 처리 진행 상황과 검증 결과 표시
- **단위 테스트·고정 평가 사례:** 검증 기능 확인 및 개선 전후 비교

## 7. 검증 계획 및 예상 한계

같은 근거와 답변 사례를 기존 검증기와 개선 검증기에 각각 입력해 비교한다. 정상 답변 외에도 수치 오류, 시스템 간 수치 혼동, 상태 불일치, 항목 누락, 미확인 시스템 등의 사례를 준비한다.

측정 지표는 ‘오류 답변 탐지율’, ‘정확한 답변의 보류율’, ‘재작성 횟수’, ‘전체 응답 시간’으로 정한다. 마지막 두 지표는 실제 모델을 연결한 실행에서 측정한다. 규칙 검사만의 지연 시간과 전체 응답 시간은 구분해서 기록한다.

이번 개선은 모니터링 상태·수치와 정해진 답변 항목을 우선 검증한다. 원인·조치의 의미적 정확성 전체를 보증하지 않으며, 정확한 자유형 답변도 형식 때문에 보류될 수 있다. 또한 제공된 모니터링은 샘플 데이터이므로 실제 운영 환경의 성능으로 해석하지 않는다.
